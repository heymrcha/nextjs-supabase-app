# 모임 이벤트 관리 MVP — 제품 요구사항 정의서 (PRD)

- 문서 버전: v1.1 (2026-09-29)
- 상태: 설계 확정 (Phase 1 착수 가능)
- 가칭: **모임장**

> v1.1 변경: 이벤트 삭제·링크 만료·명단 공개 범위 확정, 연락처 수집 제외 확정, **미정 확정 기한**·**참석/불참/미정 3분류 명단**·**응답 변경 이력** 추가.

---

## 1. 문제 정의

수영·헬스·친구 모임 등 소규모 모임의 **주최자 한 사람에게 운영 부담이 몰린다.** 현재는 대부분 카카오톡 단체방 하나로 모든 걸 처리한다.

| 주최자의 일 | 카톡에서 벌어지는 일                                       |
| ----------- | ---------------------------------------------------------- |
| 공지        | 올린 공지가 수다에 밀려 사라짐. "몇 시였죠?"가 매번 반복됨 |
| 참석자 파악 | "참석이요"가 흩어져 수기로 세고, 정원·마감을 놓침          |
| 정산        | 영수증 사진 + 계산기 + "입금했어요"를 손으로 대조          |
| 카풀        | 누가 차를 내고 누가 타는지 스레드가 꼬임                   |

**핵심 통증은 "집계"다.** 정보를 뿌리는 건 카톡이 잘한다. 흩어진 응답을 **하나의 표로 모으는 일**을 아무도 대신해 주지 않는다.

### 우리가 푸는 문제 (한 문장)

> 주최자가 링크 하나를 공유하면, 참석 여부와 정산 현황이 자동으로 집계되는 이벤트 페이지.

---

## 2. 타깃 사용자

| 구분                   | 설명                                               | 핵심 니즈                                  |
| ---------------------- | -------------------------------------------------- | ------------------------------------------ |
| **주최자 (Primary)**   | 5~30명 규모 모임을 정기적으로 여는 사람. 총무 겸함 | 수기 집계 제거, 정산 독촉 스트레스 감소    |
| **참여자 (Secondary)** | 모임에 초대받은 사람                               | **가입 없이** 빠른 응답. 내 금액·계좌 확인 |

### 설계를 가르는 결정 사항 (확정)

1. **참여자는 가입하지 않는다.** 주최자만 로그인한다. 참여자는 공유 링크 + 이름 입력으로 응답한다.
2. **단발 이벤트만 다룬다.** 정기 모임(반복 일정) 모델은 MVP 범위 밖이다.
3. **MVP 기능은 공지 / 참석 관리 / 정산** 세 가지다. **카풀은 Phase 3으로 미룬다.**
4. **연락처(전화번호·뒷자리 등)를 일절 수집하지 않는다.** 식별은 `이름 + 브라우저 쿠키`로만 한다.
5. **참석자 명단은 참석/불참/미정 모두 전체 공개한다.**
6. 이벤트 **삭제는 주최자만** 가능하며, **2단계 확인**을 거친다.
7. 공유 링크에 **만료 시각을 둘 수 있다.**

> **카풀을 뺀 이유:** 카풀은 참여자끼리 서로를 알아야 성립하는 기능(누가 어느 차에 타는지)이라, 게스트 참여 모델에서 신원 문제를 가장 먼저 건드린다. RSVP 데이터가 먼저 쌓여야 카풀 UI가 의미를 가지므로 순서상 뒤가 맞다.
>
> **연락처를 받지 않기로 한 이유:** 동명이인 구분에는 유리하지만, 수집하는 순간 개인정보 보관·파기 책임이 생기고 참여자의 입력 저항도 커진다. 5~30명 모임에서 동명이인은 드물고, 발생해도 §4.3의 경고·재연결 흐름으로 충분히 수습된다. **비용 대비 이득이 맞지 않는다.**

## 3. MVP 범위

### 포함 (In scope)

| #   | 기능                | 설명                                                                    |
| --- | ------------------- | ----------------------------------------------------------------------- |
| F1  | 이벤트 생성/수정    | 제목·일시·장소·정원·응답 마감·미정 확정 기한·준비물·공지 본문           |
| F2  | 공유 링크           | 추측 불가능한 토큰 URL (`/e/{token}`). **만료 시각 설정 · 재발급** 가능 |
| F3  | 공개 이벤트 페이지  | 로그인 없이 열람. 공지·일시·장소·현재 참석 현황                         |
| F4  | RSVP 응답           | 참석/불참/미정 + 동반 인원 + 메모. 이름으로 식별                        |
| F5  | 응답 수정           | 브라우저 쿠키 기반으로 본인 응답 재수정                                 |
| F6  | **응답 변경 이력**  | 누가 언제 무엇을 어떻게 바꿨는지 기록. 참여자는 본인 것, 주최자는 전체  |
| F7  | **미정 확정 기한**  | 미정 응답자에게 "언제까지 확정" 안내. 기한 경과자를 주최자가 따로 관리  |
| F8  | 정원·대기자         | 정원 초과 시 자동 대기 등록, 취소 발생 시 주최자가 승격                 |
| F9  | **3분류 명단 공개** | 참여자 페이지에 참석/불참/미정 명단을 탭으로 전체 공개                  |
| F10 | 참석자 관리         | 주최자용 목록/필터, 수동 추가·상태 변경 (카톡으로만 답한 사람 반영)     |
| F11 | 추가 공지           | 이벤트에 공지 타임라인 추가 (장소 변경 등)                              |
| F12 | **이벤트 삭제**     | 주최자 전용. 2단계 확인 + 30일 복구 가능                                |
| F13 | 지출 입력           | 항목명·금액·결제자 다건 입력                                            |
| F14 | 정산 분배           | 1/N · 인원수 비례 · 개별 수동 중 선택. 10원 단위 올림                   |
| F15 | 입금 체크           | 주최자가 참여자별 입금 여부 체크. 참여자는 본인 금액·계좌 확인          |

### 제외 (Out of scope — 의도적으로 뺌)

| 제외 항목                          | 이유 / 대체                                                               |
| ---------------------------------- | ------------------------------------------------------------------------- |
| 카풀                               | Phase 3. 위 설명 참조                                                     |
| 정기 모임 / 반복 일정              | Phase 4. 단발 이벤트로 검증 먼저                                          |
| 연락처·전화번호 수집               | 확정 사항 4에 의해 제외                                                   |
| 실제 결제·송금 연동 (PG, 오픈뱅킹) | 심사·수수료·정산 리스크가 MVP 대비 과도. **계좌 표시 + 수동 체크**로 대체 |
| 푸시 / 카톡 알림톡                 | 채널 심사 필요. MVP는 **주최자가 링크를 직접 공유**하는 흐름              |
| 참여자 간 채팅                     | 카톡이 이미 함. 대체하지 않음                                             |
| 사진 앨범 / 파일 업로드            | Phase 4                                                                   |
| 참여자 계정·마이페이지             | 확정 사항 1에 의해 제외                                                   |

## 4. 사용자 시나리오

### 4.1 주최자 — "토요일 자유수영 모임"

1. 로그인 → `이벤트 만들기`
2. 제목 "토요 자유수영", 10/4(토) 09:00, 올림픽수영장, 정원 12명, 응답 마감 10/3 18:00, **미정 확정 기한 10/2 22:00** 입력
3. 공지 본문에 "수영모·수경 필수, 입장료 5,000원 현장 결제" 작성
4. 생성 직후 **공유 링크 복사** → 단톡방에 붙여넣기
5. 대시보드에서 응답이 차오르는 걸 확인 (참석 9 / 미정 2 / 불참 3, 정원까지 3자리)
6. 10/3 아침, 참석자 탭에 **"확정 지연 2명"** 배지 → 필터로 확인 후 단톡방에 개인 멘션
7. 모임 종료 후 `정산` 탭에서 지출 입력 (레인 대여 60,000원, 뒤풀이 84,000원)
8. 분배 방식 `1/N (참석자 기준)` 선택 → 9명 × 16,000원 자동 계산
9. 계좌번호 등록 → 정산 공개 → 참여자 페이지에 각자 금액 표시
10. 입금이 들어오는 대로 체크박스 클릭. 미입금자만 필터로 보고 독촉
11. 정산 완료 후 필요하면 이벤트 삭제 (제목 재입력 확인 → 30일간 복구 가능)

### 4.2 참여자 — 가입 없이

1. 단톡방 링크 클릭 → 이벤트 페이지 (로그인 화면 없음)
2. 일시·장소·준비물·현재 참석자 수 확인. **참석/불참/미정 명단 탭으로 누가 오는지 확인**
3. `미정` 클릭 → 이름 "김지훈" 입력 → 완료. 화면에 **"10/2(목) 22:00까지 확정해주세요"** 안내 배지
4. 다음 날 재접속 → **이전 응답이 그대로 보임** (쿠키 인식) → `참석으로 변경`
5. 내 응답 카드 아래 **변경 이력** 표시 — "9/29 미정 → 9/30 참석"
6. 모임 후 같은 링크 접속 → 하단에 "김지훈님 정산 금액: 16,000원 / 우리은행 1002-\*\*\*-\*\*\*\*\* 홍길동" 표시

### 4.3 엣지 케이스

| 상황                    | 처리                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 정원이 찼는데 참석 신청 | 대기자로 등록. "현재 2번째 대기" 안내. 취소 발생 시 주최자에게 승격 버튼 노출 (자동 승격 안 함 — 통보 수단이 없음)      |
| 응답 마감 이후 접속     | 폼 비활성화, "응답이 마감되었습니다. 주최자에게 문의하세요". 명단·정산은 계속 열람 가능                                 |
| **미정 확정 기한 경과** | 참여자 화면에 "확정 기한이 지났습니다" 경고. **자동으로 불참 처리하지 않는다.** 주최자 화면에서 `확정 지연` 필터로 노출 |
| **링크 만료 후 접속**   | 전용 안내 화면 ("이 링크는 만료되었습니다"). 이벤트 내용·명단 모두 비공개. 주최자는 만료 연장·재발급 가능               |
| 같은 이름이 이미 있음   | 차단하지 않고 경고 ("김지훈님이 이미 응답했습니다. 본인이 맞다면 기존 응답 수정을 눌러주세요")                          |
| 쿠키가 지워진 채 재방문 | 이름 입력 시 동명 응답을 찾아 "본인이 맞나요?" 확인 후 재연결. 재연결도 변경 이력에 기록                                |
| 카톡으로만 답한 사람    | 주최자가 참석자 탭에서 **수동 추가** (F10). 정산 대상에 동일하게 포함. 이력에 `주최자 대행`으로 남김                    |
| 주최자가 이벤트 취소    | 상태를 `cancelled`로. 공개 페이지에 취소 배너, 폼 차단. 명단·정산은 열람 유지                                           |
| **삭제된 이벤트 링크**  | 404 대신 "종료되어 더 이상 볼 수 없는 모임입니다" 안내                                                                  |
| 링크가 외부에 유출      | 토큰 재발급으로 기존 링크 즉시 무효화                                                                                   |

## 5. 정보 구조 및 화면 설계

### 5.1 라우트 맵

| 경로                          | 접근     | 내용                                |
| ----------------------------- | -------- | ----------------------------------- |
| `/`                           | 공개     | 랜딩. 가치 제안 + 로그인 CTA        |
| `/auth/*`                     | 공개     | 기존 인증 흐름 (이미 구현됨)        |
| `/dashboard`                  | 주최자   | 내 이벤트 목록 (예정 / 지난)        |
| `/events/new`                 | 주최자   | 이벤트 생성 폼                      |
| `/events/[id]`                | 주최자   | 관리 화면 — 탭 3개                  |
| `/events/[id]?tab=guests`     | 주최자   | 참석자 관리                         |
| `/events/[id]?tab=settlement` | 주최자   | 정산                                |
| `/events/[id]/edit`           | 주최자   | 이벤트 정보 수정 · 링크 설정 · 삭제 |
| **`/e/[token]`**              | **공개** | 참여자용 페이지 + RSVP + 내 정산    |

> ⚠️ `/e/*`는 로그인 없이 열려야 하므로 **`lib/supabase/proxy.ts`의 공개 경로 허용 목록에 `/e`와 `/api/e`를 추가해야 한다.** 이걸 빼먹으면 참여자가 `/auth/login`으로 튕긴다. (기존에 `/instruments`를 추가한 것과 동일한 패턴)

### 5.2 화면별 구성

**`/dashboard` — 주최자 홈**

```
[+ 이벤트 만들기]

┌ 다가오는 모임 ─────────────────────────────┐
│ 토요 자유수영            10/4(토) 09:00     │
│ 참석 9 · 미정 2 · 정원 12   [링크 복사]     │
│ ⚠ 응답 마감 D-1 · 확정 지연 2명             │
├────────────────────────────────────────────┤
│ 금요 헬스 벙개           10/10(금) 19:00    │
│ 참석 4 · 정원 무제한      [링크 복사]       │
└────────────────────────────────────────────┘

┌ 지난 모임 ─────────────────────────────────┐
│ 9월 친구모임             정산 미완료 3명 ⚠  │
└────────────────────────────────────────────┘
```

빈 상태: "첫 모임을 만들어보세요. 링크 하나로 참석과 정산이 정리됩니다."

**`/events/[id]` — 관리 화면 (탭 1: 개요)**

- 상단: 제목·일시·장소·상태 배지 / `링크 복사` `수정` `취소`
- 요약 카드 5개: 참석 / 미정 / 불참 / 대기 / **확정 지연**
- 정원 진행 바
- 링크 상태 줄: "링크 만료 10/5 23:59 · [연장] [재발급]"
- 공지 타임라인 (추가 공지 작성 인라인 폼)

**탭 2: 참석자**

- 필터 칩: 전체 / 참석 / 미정 / 불참 / 대기 / **확정 지연**
- 테이블: 이름 · 상태 · 동반 · 메모 · **최초 응답** · **최종 수정** · 액션(상태 변경, 삭제, 대기→참석 승격)
- 행 확장 시 **변경 이력 타임라인**: `9/29 20:11 미정 → 9/30 08:02 참석 (본인)`
- `+ 직접 추가` 버튼 (카톡 응답자 반영용)
- 상단에 **이벤트 전체 활동 로그** 접이식 패널 (최근 변경 20건)

**탭 3: 정산**

- 지출 목록 (항목·금액·결제자) + 인라인 추가
- 총액 / 분배 방식 라디오 (1/N · 인원수 비례 · 개별 입력)
- 미리보기 표: 이름 · 금액 · 입금여부 체크박스
- 반올림 안내: "10원 단위 올림, 차액 480원은 주최자 부담"
- `정산 공개하기` — 누르기 전까지 참여자에게 보이지 않음
- 계좌 정보 입력 (은행 · 번호 · 예금주)

**`/events/[id]/edit` — 이벤트 수정 · 링크 · 삭제**

- 기본 정보 수정 폼
- 링크 설정: 만료 시각 (미설정 / 모임 종료 후 7일 / 직접 지정), `재발급` 버튼
- 하단 **위험 구역 (Danger Zone)** — 붉은 테두리 카드
  - `이벤트 삭제` 버튼 → 다이얼로그 (§5.3)

### 5.3 이벤트 삭제 흐름 (F12)

삭제는 참여자 응답과 정산 기록을 한 번에 없앤다. **2단계 확인을 둔다.**

## 6. 데이터 모델

### 6.1 ERD (논리)

```
auth.users ─1:N─ events ─1:N─ participants ─1:N─ participant_response_logs
                    │            │
                    ├─1:N─ announcements
                    ├─1:N─ expenses
                    ├─1:1─ settlements
                    └─────────1:N─ settlement_shares ─N:1─┘
```

### 6.2 테이블 정의

**`events`**

| 컬럼                        | 타입                 | 설명                                            |
| --------------------------- | -------------------- | ----------------------------------------------- |
| `id`                        | uuid PK              |                                                 |
| `owner_id`                  | uuid FK → auth.users | 주최자                                          |
| `title`                     | text NOT NULL        |                                                 |
| `description`               | text                 | 공지 본문 (플레인, 줄바꿈 보존)                 |
| `category`                  | text                 | `swim` \| `gym` \| `social` \| `etc`            |
| `starts_at`                 | timestamptz NOT NULL |                                                 |
| `ends_at`                   | timestamptz NULL     |                                                 |
| `location_name`             | text                 |                                                 |
| `location_url`              | text NULL            | 지도 링크                                       |
| `capacity`                  | int NULL             | NULL = 무제한                                   |
| `rsvp_deadline`             | timestamptz NULL     | 전체 응답 마감                                  |
| **`undecided_deadline`**    | timestamptz NULL     | **미정 확정 기한.** `rsvp_deadline` 이하여야 함 |
| `share_token`               | text UNIQUE NOT NULL | 22자 이상 난수 (base58)                         |
| **`link_expires_at`**       | timestamptz NULL     | **링크 만료.** NULL = 무기한                    |
| `status`                    | text NOT NULL        | `open` \| `closed` \| `cancelled`               |
| **`deleted_at`**            | timestamptz NULL     | **soft delete.** NOT NULL이면 어디에도 안 보임  |
| `created_at` / `updated_at` | timestamptz          |                                                 |

- 인덱스: `(owner_id, starts_at)`, `(share_token)`
- 모든 조회에 `deleted_at IS NULL` 조건이 붙는다. **이 조건을 빼먹는 것이 이 스키마의 대표적인 실수 지점이다** — 조회 헬퍼 함수 하나로 감싸서 개별 쿼리가 직접 쓰지 않게 한다.

**`participants`**

| 컬럼                          | 타입                               | 설명                                              |
| ----------------------------- | ---------------------------------- | ------------------------------------------------- |
| `id`                          | uuid PK                            |                                                   |
| `event_id`                    | uuid FK → events ON DELETE CASCADE |                                                   |
| `display_name`                | text NOT NULL                      | 참여자가 입력한 이름 (연락처는 받지 않음)         |
| `status`                      | text NOT NULL                      | `going` \| `not_going` \| `maybe` \| `waitlisted` |
| `headcount`                   | int NOT NULL DEFAULT 1             | 본인 포함 인원                                    |
| `note`                        | text NULL                          | **주최자에게만 노출**                             |
| `edit_token`                  | text UNIQUE NOT NULL               | 게스트 본인 확인용. 쿠키에 저장                   |
| `added_by_owner`              | boolean DEFAULT false              | 주최자가 수동 추가했는지                          |
| `responded_at` / `updated_at` | timestamptz                        | 최초 응답 / 최종 수정                             |

- 인덱스: `(event_id, status)`, `(edit_token)`

**`participant_response_logs`** (신규 — F6 응답 변경 이력)

| 컬럼             | 타입                                     | 설명                                                                                           |
| ---------------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `id`             | uuid PK                                  |                                                                                                |
| `event_id`       | uuid FK → events ON DELETE CASCADE       | 이벤트 단위 활동 로그 조회용 (비정규화)                                                        |
| `participant_id` | uuid FK → participants ON DELETE CASCADE |                                                                                                |
| `action`         | text NOT NULL                            | `created` \| `status_changed` \| `headcount_changed` \| `promoted` \| `reclaimed` \| `removed` |
| `from_status`    | text NULL                                |                                                                                                |
| `to_status`      | text NULL                                |                                                                                                |
| `from_headcount` | int NULL                                 |                                                                                                |
| `to_headcount`   | int NULL                                 |                                                                                                |
| `actor`          | text NOT NULL                            | `guest` \| `owner` — 본인이 바꿨는지 주최자가 대신했는지                                       |
| `created_at`     | timestamptz NOT NULL DEFAULT now()       |                                                                                                |

- 인덱스: `(participant_id, created_at DESC)`, `(event_id, created_at DESC)`
- **append-only.** 수정·삭제하지 않는다. 이력이 사후에 바뀌면 이력의 의미가 없다.
- 기록 시점: RSVP 생성/수정, 주최자의 상태 변경, 대기자 승격, 쿠키 재연결, 참여자 삭제.
- 기록 방식은 **Route Handler / Server Action에서 명시적으로 insert** 한다. DB 트리거를 쓰지 않는다 — `actor` 값이 애플리케이션 문맥(쿠키 인증인지 주최자 세션인지)에만 존재하기 때문이다.

**`announcements`** — `id`, `event_id`, `body`, `created_at`

**`expenses`** — `id`, `event_id`, `label`, `amount numeric(12,2)`, `payer_name`, `created_at`

**`settlements`** (이벤트당 1행) — `id`, `event_id UNIQUE`, `split_method`(`equal` \| `by_headcount` \| `custom`), `bank_name`, `account_number`, `account_holder`, `published_at NULL`, `memo`

**`settlement_shares`** — `id`, `event_id`, `participant_id`, `amount numeric(12,2)`, `is_paid boolean`, `paid_at`, UNIQUE `(event_id, participant_id)`

### 6.3 상태 판정 규칙 (파생 값 — 컬럼으로 저장하지 않음)

| 판정          | 조건                                                                                |
| ------------- | ----------------------------------------------------------------------------------- |
| 응답 가능     | `deleted_at IS NULL` AND `status = 'open'` AND (`rsvp_deadline` 미설정 또는 미도래) |
| 링크 유효     | `deleted_at IS NULL` AND (`link_expires_at` 미설정 또는 미도래)                     |
| **확정 지연** | `participants.status = 'maybe'` AND `undecided_deadline < now()`                    |
| 정산 공개     | `settlements.published_at IS NOT NULL`                                              |

파생 값을 컬럼에 저장하면 시간이 지나도 갱신되지 않아 조용히 틀린다. **조회 시점에 계산한다.**

### 6.4 정산 계산 규칙

```
총액 = SUM(expenses.amount)
분배 대상 = participants WHERE status = 'going'

equal        : 1인당 = 총액 / COUNT(대상)
by_headcount : 1인당 = (총액 / SUM(headcount)) × 본인 headcount
custom       : 주최자가 직접 입력

각 금액은 10원 단위 올림(ceil).
올림으로 생긴 초과분은 주최자 부담으로 표시(추가 징수 없음).
```

분배 결과는 **계산 시점에 `settlement_shares`에 스냅샷으로 저장한다.** 정산 공개 후 참석자가 바뀌어도 이미 안내한 금액이 조용히 변하면 안 되기 때문이다. 재계산은 주최자가 명시적으로 `다시 계산`을 눌렀을 때만 일어난다.

## 7. 보안 설계 — 게스트 쓰기를 어떻게 허용할 것인가

**이 MVP에서 가장 위험한 지점이다.** 로그인하지 않은 사람이 DB에 쓰기를 해야 하는데, anon 키로 RLS를 열어주면 토큰을 모르는 사람도 모든 이벤트의 참석자 목록을 긁을 수 있다.

### 채택하는 방식: 서버 경유 + RLS 전면 차단

| 계층        | 정책                                                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| RLS         | 모든 테이블 활성화. 정책은 **`owner_id = auth.uid()` 하나뿐**. anon 역할에는 정책을 만들지 않아 **모든 익명 접근이 거부**된다       |
| 주최자 경로 | 기존 `lib/supabase/server.ts` / `client.ts` 그대로. RLS가 소유권을 강제                                                             |
| 게스트 경로 | `/e/[token]` 서버 컴포넌트와 `/api/e/[token]/*` Route Handler에서만 **service role 클라이언트**(`lib/supabase/admin.ts`, 신규) 사용 |

게스트 경로의 규칙:

1. `admin` 클라이언트는 **절대 클라이언트 컴포넌트에 노출하지 않는다.** `import "server-only"`를 파일 상단에 둔다.
2. 모든 게스트 쿼리는 **반드시 `share_token`으로 이벤트를 먼저 조회**하고 (`deleted_at IS NULL` + 만료 확인 포함), 그 `event_id`로만 후속 쿼리를 건다.
3. 게스트에게 반환하는 필드는 **화이트리스트로 명시**한다. `select("*")` 금지 — `edit_token`, `owner_id`가 새어나간다.
4. 명단에는 **이름·상태·동반 인원만** 내려준다. `note`와 `edit_token`은 주최자 경로 전용이다.
5. 응답 수정은 httpOnly·SameSite=Lax 쿠키의 `edit_token`과 URL 토큰이 **둘 다 일치할 때만** 허용한다.
6. 변경 이력 조회도 같은 원칙 — 게스트는 **자기 `participant_id`의 로그만** 받는다. 이벤트 전체 로그는 주최자 전용이다.
7. RSVP 엔드포인트에 **IP + 토큰 기준 rate limit**을 건다 (MVP: 분당 10회, 이후 Upstash 등으로 이전).

환경 변수가 하나 늘어난다: `SUPABASE_SECRET_KEY` (service role). **`NEXT_PUBLIC_` 접두사를 붙이면 안 된다.**

> **대안이었던 방식과 기각 이유:** RLS 정책에서 `share_token`을 조건으로 쓰는 방법은 정책이 테이블마다 복잡해지고, 자식 테이블(participants, shares, logs)마다 JOIN 조건을 중복 작성해야 해 실수 한 번에 전체가 열린다. 서버 경유가 검증 지점을 한 곳으로 모은다.

## 9. 성공 지표

MVP는 "많이 쓰이는지"가 아니라 **"주최자의 집계 노동이 실제로 사라졌는지"**로 판단한다.

| 지표                | 측정                                                              | 목표 (첫 4주) |
| ------------------- | ----------------------------------------------------------------- | ------------- |
| **활성화**          | 이벤트를 만들고 **링크를 실제로 복사**한 비율                     | 80%           |
| **핵심 성립**       | 이벤트당 RSVP 응답 수 ≥ 5 인 비율                                 | 60%           |
| **응답 속도**       | 링크 공유 후 첫 24시간 내 응답률                                  | 60%           |
| **미정 해소율**     | 미정 응답자가 **확정 기한 내** 참석/불참으로 바꾼 비율            | 70%           |
| **정산 도달**       | 지출을 입력한 이벤트 중 **전원 입금 체크 완료** 비율              | 50%           |
| **재사용 (북극성)** | 첫 이벤트 주최자가 **2주 내 두 번째 이벤트**를 만든 비율          | 40%           |
| **수기 이탈**       | 주최자가 참석자를 `직접 추가`한 비율 (높으면 참여자 UX 실패 신호) | 20% 미만      |

정성 검증: 주최자 5명 사용 후 인터뷰 — "이번 모임에서 카톡으로 사람 세는 일을 했나요?"
