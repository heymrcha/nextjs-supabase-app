# 미해결 질문 결론 (PRD §11 · T-605)

2026-10-02. PRD §11의 4개 질문에 대한 **현재 결론**이다. 넷 다 "실사용 1건으로 판단"을 전제했는데,
실제 모임을 한 번 치른 것이 아니라 Phase 6 검증(`phase6-verification.md`)에서 각 규칙을
재현해 본 수준이다. 그래서 결론마다 **무엇을 보고 그렇게 판단했는지와 번복 조건**을 함께 적는다.

---

## 1. 게스트 쿠키 180일은 적절한가?

**유지한다(180일).**

쿠키는 이벤트별로 분리돼 있고(`moim_gk_<event_id 앞 8자>`) 이름·연락처를 담지 않는다. 담긴 것은
무작위 `guest_key` 하나이므로, 오래 남아도 유출 시 영향은 "그 이벤트에서 그 사람의 응답을 수정할
수 있다"에 그친다. 반대로 짧게 잡으면 모임 직전 재방문에서 본인 응답을 못 찾아 중복 응답이 쌓이고,
그 정리는 주최자 몫이 된다 — 검증 2·3행에서 본 그대로다.

번복 조건: 한 사람이 같은 이벤트에 여러 행을 만드는 사례가 실제로 반복되면, 기간이 아니라
"이름 충돌 시 기존 응답 이어받기" 쪽을 먼저 손본다. 기간 단축은 그 문제를 악화시킨다.

## 2. 정원 초과를 대기 순번으로 받는 것이 맞는가, 참석 선택 자체를 막는 것이 맞는가?

**대기 순번으로 받는 현재 설계를 유지한다.**

막는 쪽은 두 가지가 걸린다. 첫째, 게스트가 "참석하고 싶다"는 의사를 남길 방법이 사라진다 —
주최자가 정원을 늘릴지 판단할 근거도 같이 사라진다. 둘째, 정원 도달 여부는 동시에 들어오는 응답
사이에서 흔들리므로, 막으려면 제출 시점에 잠금과 거부 분기가 필요하고 "거부당한 사람"이라는
처리하기 까다로운 상태가 생긴다. 지금은 `attending`으로 받고 표시만 구분하므로 이런 상태가 없다.

검증 4행에서 정원 5명·참석 7명이 `대기 1번`, `대기 2번`으로 응답 순서대로 매겨지는 것을 확인했고,
게스트·주최자 화면이 같은 번호를 보여 준다.

번복 조건: 주최자가 "대기 순번도 참석자로 세는 바람에 정산 인원이 틀렸다"고 느끼면, 정산 대상을
`attending` 전체가 아니라 정원 이내로 좁히는 선택지를 다시 꺼낸다. 지금은 **정원 초과분도 정산
대상에 포함**된다는 점을 주최자가 알 수 있게 화면에서 대기 순번을 보여 주는 것으로 갈음한다.

## 3. 미정 기한 경과자를 정산 대상에서 제외하는 규칙이 주최자 직관에 맞는가?

**맞다. 유지한다.**

핵심은 "제외"가 별도 규칙이 아니라는 것이다. 정산 대상은 `status = 'attending'`뿐이고, 미정은
기한이 지나도 **자동으로 참석이 되지 않는다**(검증 7행). 그래서 "기한 초과자는 정산에서 빠진다"는
문장은 따로 구현된 규칙이 아니라 두 규칙의 결과다. PRD §6에 있던 "참석이고 기한초과가 아닌"이라는
조건은 항상 참인 사문이라 T-502에서 삭제했다.

주최자 직관과 어긋날 수 있는 지점은 오히려 반대쪽이다 — 미정인 채 실제로 참석한 사람이 있으면
주최자가 그 사람을 `attending`으로 바꿔 줘야 정산에 들어간다. 이 조작은 응답 관리 화면에서 된다.

번복 조건: 모임 후 "미정이었는데 온 사람"을 매번 손으로 바꿔야 한다면, 정산 화면에서 미정자를
한 번에 참석으로 넘기는 보조 동작을 검토한다. 자동 전환은 여전히 하지 않는다.

## 4. 링크 재발급 시 기존 응답을 유지할지 초기화할지

**유지한다(현재 설계 그대로).**

재발급의 목적은 "링크가 엉뚱한 곳에 퍼졌다"를 끊는 것이지 모은 응답을 버리는 것이 아니다.
`regenerate_share_token`은 `share_token` 컬럼만 바꾸므로 응답·공지·정산은 그대로 남고, 옛 링크는
즉시 만료 화면으로 떨어진다.

응답을 지우는 선택지는 게스트 쿠키와도 어긋난다. 쿠키 이름이 토큰이 아니라 `event_id` 기반이라
(D1) 재발급 후에도 게스트는 본인 응답을 그대로 찾는다 — 응답만 지우면 쿠키는 남고 가리킬 대상이
없어진다.

번복 조건: 없음에 가깝다. 응답을 비우고 싶은 상황은 "이벤트를 다시 연다"에 가까우므로 새 이벤트를
만드는 것이 맞다.

## 완주 시나리오 (Phase 6 완료 기준)

주최자 1명 + 게스트 다수로 **개설 → 응답 → 공지 → 정산 → 입금 → 공개** 전 구간을 돌렸다.

| 구간 | 수행                                                           | 비고                                                                                             |
| ---- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 개설 | SQL로 검증용 이벤트 생성                                       | 생성 폼 자체는 T-203에서 확인                                                                    |
| 응답 | 게스트 폼으로 실제 제출 1건(375px) + RPC로 8건                 | 제출 후 이벤트 페이지로 이동, "내 응답"에 반영, 쿠키는 `document.cookie`로 읽히지 않음(httpOnly) |
| 공지 | 주최자 화면에서 작성 → 게스트 페이지 상단 반영 확인            |                                                                                                  |
| 정산 | 비용 2건 → 1인당 ₩7,430(7명) → 참석 변동 후 재계산 ₩8,670(6명) | 입금 1건 승계 확인                                                                               |
| 입금 | 입금 현황 1/6, 미수금 ₩43,350                                  | **대시보드 배지와 값 일치**                                                                      |
| 공개 | 공개 후 게스트가 본인 분담금만 확인                            | 비공개로 되돌리면 계좌까지 사라짐                                                                |

데스크톱(1280px)과 모바일 폭(375px) 양쪽에서 확인했다. 주최자 화면은 로그인된 Chrome 세션,
게스트 화면은 별도 브라우저(쿠키 없는 최초 방문자 상태)로 봤다.
